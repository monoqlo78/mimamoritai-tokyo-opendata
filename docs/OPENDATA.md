# 使用しているオープンデータ

「見守り隊 / CareRoute AI」は、カメラを使わずに離れて暮らす家族を見守ります。
家の中のセンサーだけでは「暑いのに冷房が止まっている」ことに気づけません。
**屋外の公的オープンデータ**と、**家の中の電力の実測**を掛け合わせて初めて、
その日いちばん危ない状態を先回りして知らせられます。

#### 防災情報を「速報の焼き直し」にしないための設計

緊急速報メールは全員に届く。だからこの通知は**警報そのものを伝えない**。伝えるのは2文目 ——

> 東京都に土砂災害警戒情報が出ています。お母さんのお宅では07:15に家電の利用がありました。

家電が動いた時刻は、このアプリしか持っていない。警報の再送は無価値だが、**警報と安否を1通に束ねること**には価値がある。

そのために次を守っている。

- **絞る**：注意報・警報は送らない。地震は東京の震度が5弱以上のときだけ。九州の震度3を東京の家族に送れば、通知はミュートされ、熱中症アラートも一緒に沈黙する
- **1件だけ**：大雨特別警報と土砂災害警戒情報は同時に出る。重大な方を1通だけ送る
- **重複させない**：警報は数時間出たままになる。発表時刻＋種別＋地域をキーに、1回だけ送る
- **捏造しない**：家電の記録がなければ「まだ確認できていません」と書く。**沈黙を「無事」にも「異常」にも丸めない**

#### 警報が出ているのに家が暗い ―― 唯一「至急」を出す条件

警報は「危ない場所」を教えてくれるが、「その人がそこにいるか」は教えてくれない。
このアプリだけが持っているのは後者で、**警報中に電気が落ちていること**は
「屋内でやり過ごしている」と「外にいるかもしれない」を分ける唯一の材料になる。

> 東京都に顕著な大雨に関する気象情報が出ています。お母さんのお宅では16時ごろからの3時間、
> 電気の使用がいつもの5％まで落ちています。外出されているかもしれません。
> すぐにご連絡のうえ、安全な場所にいるかご確認ください。

判定は決定的で、AIは一切関与しない（[`RiskAssessmentService.DetectQuiet`](../src/MimamoriTai.Core/Application/RiskAssessmentService.cs)）。
誤報の代償が「電話しなくてよい人に電話させる」で済むとはいえ、鳴りやすい通知は無視されるため、次で絞っている。

| 条件 | 値 | 理由 |
|---|---|---|
| 直前の完全な時間 | 3時間 | 買い物1回では鳴らない長さ |
| いつもとの比 | 25%以下 | 「静かな午後」ではなく「誰もいない」水準 |
| その時間帯の平常値 | 30Wh以上 | 平常値がほぼ0の時間帯は比を取っても意味がない |
| 平常値の日数 | 3日以上 | 導入2日目の世帯を「留守」と判定しない |
| 睡眠時間帯（22–6時） | 対象外 | 毎晩鳴る通知は必ずミュートされる |
| 計測中の時間 | 対象外 | 進行中の1時間は必ず電力が足りず、常時発報してしまう |

平常時の通知（ご家族の様子を確認しましょう）とは**別のキーで重複排除**している。
先に平常時の通知を送ったあとで電気が落ちることがあり、それは新しい情報だからである。

実装は
[`src/MimamoriTai.Infrastructure/OpenData/JmaDisasterAdvisoryProvider.cs`](../src/MimamoriTai.Infrastructure/OpenData/JmaDisasterAdvisoryProvider.cs)、
通知は
[`WatchAlertService.TrySendDisasterNoticeAsync`](../src/MimamoriTai.Core/Application/WatchAlertService.cs) です。


取得・解析の実装は
[`src/MimamoriTai.Infrastructure/OpenData/TokyoHeatAdvisoryProvider.cs`](../src/MimamoriTai.Infrastructure/OpenData/TokyoHeatAdvisoryProvider.cs)、

### 熱中症ガードの考え方

```
環境省WBGT（オープンデータ）  ×  エアコンのプラグが「待機中」（通電しているのに 0W）
        ↓
「厳重警戒なのに、冷房が動いていません」  → 家族へ先回りで通知
```

高齢者の熱中症は**住居内での発生が 56.6%**（下記データ3）。
つまり「外が危険」だけでも「家電が止まっている」だけでも足りず、
**その2つが重なった瞬間**こそが、カメラを置かずに救える一点です。

判定は**すべて決定論的なルール**で行い、LLMには任せていません。
命に関わる判断を確率的な生成に委ねないという設計方針です。

| 暑さ指数 | 区分 | 冷房が動いていないとき | 単独での結果 |
|---|---|---|---|
| 31以上 | 危険 | +60点 | それだけで「高」 |
| 28以上 | 厳重警戒 | +45点 | 他の兆候と重なれば「高」 |
| 28未満 | — | 加点なし | — |

配慮している点:

- **冷房機器が1台も登録されていない世帯には加点しない。** 登録していない家電を「止まっている」と責めるのは筋違いなので、暑さ指数を伝えるだけにとどめます。
- **消費電力が取れないプラグは「動いている」側に倒す。** 稼働中のエアコンを誤って「止まっている」と断じるより安全です。
- **30分以上古い測定値は使わない。** オフラインになったプラグの古い値が現在を代弁しないようにしています。
- **取得に失敗しても直前のキャッシュを返す。** 猛暑日にAPIが落ちた瞬間に見守りも止まる、という事態を避けます。
- WBGTの提供期間は**4月第4水曜〜10月下旬**で、冬季は404が返ります。これは異常ではないため、警告ではなく情報ログとして扱います。

### 寒さガード ―― 見守りが半年で止まらないために

暑さ指数のデータは**1年の半分しか存在しません**。
本選（10月）から社会実装期間（11月〜3月）にかけては、熱中症の判定軸そのものが消えます。
そこで**通年取得できる気象庁の気温**を主軸に置き、同じ構造をそのまま冬に通しました。

```
気象庁の気温（オープンデータ）  ×  暖房のプラグが 0W
        ↓
「5℃なのに、暖房が動いていません」  → 家族へ通知
```

冬に電力で見守る意味は、熱中症の裏返しではありません。
**節電のために暖房を我慢している**という、本人が家族に言わない事実が、
電力の数字にだけ現れるからです。カメラなしの見守りが最も強いのはここです。

| 気温 | 区分 | 暖房が動いていないとき | 根拠 |
|---|---|---|---|
| 5℃未満 | 厳しい冷え込み | +60点（単独で「高」） | ヒートショック（消費者庁：冬季の入浴中死亡は高齢者に集中） |
| 5〜10℃ | 冷え込み | +45点 | WHO住宅と健康ガイドライン：**室温18℃以上**を強く推奨 |
| 10〜15℃ | 肌寒い | 加点なし（一言だけ） | — |
| 15℃以上 | — | 何も言わない | — |

さらに、**翌朝の最低気温**を気象庁の予報から読み、冷え込む朝の**前夜のうちに**
「今夜のうちに脱衣所を暖めておきましょう」と伝えます。
脱衣所は、寒い朝になってからでは暖められません。
**検知ではなく予防**に回れる数少ない一点です。

配慮している点:

- **暖房の「つけっぱなし」判定を、寒い日は2時間から8時間に緩めます。** 冬に暖房をつけている高齢者を2時間で咎めるのは、見守りではなく小言です。ただし完全には外しません（夜通しの火災リスクは実在するため）。
- **暖房機器が未登録の世帯には加点しません。** 熱中症ガードとまったく同じ扱いです。
