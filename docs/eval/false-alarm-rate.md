# 誤報率

<!-- RiskEvaluationTests が生成。手で書き換えないこと。 -->

見守りサービスの寿命を決めるのは検知率ではなく誤報率である。何でもない日に通知が飛べば
家族は通知を切り、切られた瞬間に検知率はいくつであっても意味を失う。だからここでは
「危険をどれだけ捕まえたか」と同じ重さで「何でもない日にどれだけ黙っていられたか」を測る。

判定は決定的な純関数なので、この表はLLMも外部APIも使わず毎pushでCIが再計算する（通知の閾値: Medium 以上）。

| | 件数 | 通知した | 通知しなかった |
| --- | ---: | ---: | ---: |
| 平常日（通知は不要） | 32 | **0**（誤報） | 32 |
| 異常日（通知が必要） | 20 | 20 | **0**（見逃し） |

- **誤報率 0.0%** (0/32)
- **見逃し率 0.0%** (0/20)

## この数字の限界（先に書いておく）

1. これは実世帯の記録ではなく、手で書いた合成シナリオである。測っているのは
   「規則が宣言どおりに振る舞うか」であって「現実の高齢者宅で誤報が出ないか」ではない。
   後者を言うには実運用データが要る。
2. 期待値は公開している閾値を踏まえて書いているので、これは仕様書と回帰ゲートを
   兼ねるものであり、独立した第三者検証ではない。
3. 価値は境界にある。閾値の10分手前の寝坊、猛暑日に8時間動くエアコン、寒い日に
   6時間動くヒーター、就寝中の平坦な電力 — うっかりした変更がまず壊すのはここで、
   壊れた瞬間にプルリクエストのCIが赤くなる。

## この評価が最初の実行で見つけた欠陥

表を緑にするために書いた道具ではない。最初に走らせた時点で、出荷済みの規則に
実際の誤報が1件見つかった。

「活動量が普段より少ない」の判定が、**進行中の一日の集計を、終わった一日の平均と**
**比べていた**。朝6時なら少なくて当たり前なので、全世帯で毎朝鳴る。しかも利用回数が
1回以上あることが条件なので、鳴る引き金は**起きて照明を点けたこと**だった。
毎朝鳴る通知は読まれなくなり、読まれなくなった通知は本当の日に効かない。

修正は `RiskAssessmentService.LowActivityEarliestHour`。一日がその判断に足るだけ
進むまでこの比較を行わない。朝の異変は元々「起床が遅い」規則が直接見ている。
n-31 / n-32 がこの欠陥を再現するケースとして残してある。
